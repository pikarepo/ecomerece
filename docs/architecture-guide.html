00

From zero — the words first

If you have never written code in this style, start here. Nothing on this page is specific to this repo yet: it is only the vocabulary the other seven sections assume you already own.

The whole style in four sentences. Business rules live in one object per thing, and only that object may change it. The database sits behind an interface the domain defines, so the domain never imports Mongoose. HTTP lives at the edge and only translates. A module reaches another module through a published contract — never through an import of its files. Every rule in §01–§07 is a consequence of those four.

You already know the shape of a web request: something arrives, something is read or written, a response goes back. The question this guide answers is where each of those steps is allowed to live, so that twelve endpoints later the rules are still in one place. Here is every word the rest of the page uses, in plain language, with the file that owns it.

The thirteen words. Read the middle column first; the right column is where to look when you want the code.

Controller Translates a request into arguments and the answer into a status code and JSON body. No business rules are allowed here. apps/api/modules/<name>/presentation/<name>.controller.ts

Composition root The single place where all module factories are called and wired to each other. There is exactly one. apps/api/composition-root.ts

01

The mental model

Four layers, one direction. A module is not a folder of endpoints — it is an aggregate plus the machinery to expose it.

                    ┌──────────────────── packages/domain ────────────────────┐
                    │  aggregate · value objects · domain events · repo port   │
                    │  read models          (no Mongoose, no Hono, no Zod)     │
                    └───────────────────────────┬─────────────────────────────┘
                                                │ implements the port
                    ┌───────────────────────────▼─────────────────────────────┐
   apps/api/modules │  infrastructure/     model · mapper · repository           │
   /<name>/         └───────────────────────────┬─────────────────────────────┘
                                                │ injected into
                    ┌───────────────────────────▼─────────────────────────────┐
                    │  application/        queries · handlers · internal svc   │
                    │                      app service (load→mutate→save→emit) │
                    └───────────────────────────┬─────────────────────────────┘
                                                │ exposed through
                    ┌───────────────────────────▼─────────────────────────────┐
                    │  presentation/       controller · messages · routes      │
                    │  <name>.module.ts    factory: build graph + register     │
                    └─────────────────────────────────────────────────────────┘

R1 Dependencies point inward

Domain knows nothing. Infrastructure implements domain ports. Presentation depends on application. Never the reverse.

R2 Server owns the ID

On every create path the API generates Id.create(). A client-supplied ID is only for addressing something that already exists.

R3 Buses are injected

No module imports a bus singleton. createApplication() builds one query bus and one event bus and passes them through deps.

R4 Cross-module = contracts

Query classes, ports and actor types live in packages/contracts. Anything else is an architecture violation.

R5 Events after persistence

Aggregates raise; app services publish after the write. If the write is transactional, publish after the commit.

R6 Reads may skip the aggregate

A query handler can map a document straight to a read model. Only writes must go through an aggregate.

Vocabulary. Aggregate — the only thing allowed to change state, raises events. VO — validated immutable value (Id, Money, Quantity, Title, Reason). Read model — flat shape for responses. App service — use case. Internal service — cross-module verification helper that returns facts, not errors. Module factory — composition function; the only place a graph is built.

03

Build a module, step by step

We are adding coupon: a vendor-scoped discount code. One aggregate, one create endpoint, one read query, one public verification query other modules can execute, one event. Follow the order exactly — each step compiles against the previous one.

Before you start. bun install once. Keep two terminals: one running bun test --watch, one free for bun run typecheck and bun run arch. Typecheck after every file; it is cheaper than debugging a half-built graph.

01

Contract first — decide the boundary

Before writing an aggregate, decide what other modules are allowed to ask. Here it is one question: “is this coupon code usable for this vendor?” That becomes a contract query class.

Then add it to both barrels:

Why the class lives in contracts, not in the module: the query bus keys handlers by the class object. If the consumer imports one copy and the provider registers another, the lookup silently misses. One class, one import path, no ambiguity.

Naming. Use the question shape: Verify…AndGetQuery when the caller needs the facts plus a validity flag, Ensure…Query when invalidity should throw, Get…Query for plain reads. This mirrors the existing 14 contract queries.

02

Domain events — name what happened

Events are past-tense facts. One class per fact, one file per class, aggregated by events/index.ts.

Why not publish from inside the aggregate? The aggregate must stay pure and synchronous. It records events; the app service decides when the outside world hears about them — after the save, or after the commit.

03

Aggregate — private state, public verbs

Three obligations: a static create, a static rehydrate used only by the mapper, and command methods that validate then this.raise(...). State is private; expose getters, not setters.

Why rehydrate exists: constructing from persistence must not fire events or bump versions. Keeping it a separate static makes “did this come from the DB?” explicit. Note the private constructor — the only doors in are create and rehydrate.

05

Persistence model — Mongo shape, not domain shape

Mongoose schema with a string _id (UUID v7), explicit version for optimistic locking, and versionKey: false so Mongoose does not add __v on top of it.

Why strings for IDs and numbers for dates? The existing collections store UUID strings and epoch millis. Matching them keeps mappers dumb and pagination cursors comparable. Follow whatever the neighbouring collection does — consistency beats preference.

06

Mapper — the only place shapes change

Static object, pure functions, no DB calls. The repo's mapper naming is persistenceToAggregate, aggregateToPersistence, aggregateToReadModel, persistenceToReadModel, plus a response mapper when the HTTP shape differs from the internal read model.

Repo reality check. Older notes describe four differently named methods (toDocument, toUpdatePayload, fromDocument, fromDocuments). The actual code in apps/api/modules/*/infrastructure uses the four names above, plus a response mapper where the HTTP shape differs. Follow the code — and when you edit an existing mapper, keep its method names.

07

Repository — implement the port, own the locking

Extend MongoRepository<TPersistence> for session-aware primitives (findById, findOne, updateOne, paginateByCursor). Writes go through Save with a version check.

Why ConcurrencyError on zero modified docs: the update filters on the loaded version. If somebody else wrote in between, nothing matches and the caller gets a 409 instead of silently clobbering. Do not drop the version predicate to “fix” a failed save.

$set must not include version. The update uses $inc: { version: 1 }; putting version in the aggregateToPersistence payload makes Mongo reject the write for conflicting paths, and leaving it out is what makes the version filter meaningful.

08

Zod DTO — validate at the edge

Request shapes live in packages/shared/request-dtos/<module>/ and are exported through that folder's index.ts.

Why not validate in the controller? You do — via this.body(c, schema). But the schema lives in shared so the web SDK and mobile can reuse the same contract. Never duplicate a request shape in the API module.

09

Queries and handlers

Two kinds of query file:

  • Contract re-export — the class lives in packages/contracts; this file exists so the module imports its own query by a local path (and so nobody is tempted to redeclare it).
  • Local query — only this module executes it; define it here.

Handlers are thin. They either call an internal service (facts, no throwing for “not found”) or the app service (read projections).

Why an internal service at all? The query handler should not know how validity is computed, and the app service should not expose a “maybe” API to other modules. The internal service is the only thing that can answer “is this valid?” without throwing. Keep it free of bus calls so adapters and handlers can share it.

10

App service — the use case

The shape is always: generate IDs → build VOs → call the aggregate → persist → publish → return a message. Extend BaseService for guards and helpers.

Do not accept an ID on a create path. Id.create() with no argument generates a UUID v7. Passing data.id from the client into a create is a bug even if the DTO happens to contain one. Client IDs are only for update/delete/lookup.

11

Controller + routes — thin, typed, guarded

Controllers extend BaseController<AppService>, parse with Zod, and return through the response helpers. No business logic, no repository calls.

Why the controller is a class of arrow functions: Hono mounts controller.method directly. Arrow fields keep this bound without .bind() calls in the route table. Do not use regular methods here.

You have now written every box in the write path, so here is the whole request. It differs from the read in §02 in two places: the guards are stricter, and the last three steps happen after the document exists.

  • Three ids, three meanings. Id.create() generates the coupon id; Id.create(actor._id) and Id.create(data.vendorId) wrap ids that already exist. The body may name a vendor — it may never name the new document.
  • Value objects before the aggregate. Quantity.create and ExpirationDate.create run as arguments, so a bad percentOff or a Date in the past throws before CouponAggregate.create is even entered.
  • Save, then publish — never the reverse. A subscriber to coupon.created can immediately FindByIdOrThrow the coupon it was told about. Swap the two lines and that read races the insert.
  • One insert needs no transaction. §4.5 applies to order lines. Here the whole write is one document, which is either there or not.
  • this.created(), not this.ok(). Same { success, data } envelope, status 201.

The other half of the write path. Create was build-then-insert: nothing existed before the call. Redemption is load-modify-save: the aggregate is already in the database, so the service has to fetch it, let it guard its own invariants, and put it back. Same layers, different shape — and two failure modes create can never produce.

  • Load, mutate, save — in that order. The service never builds the aggregate here; it asks the repository for it, so the guards run against real persisted state.
  • 404 and 400 are different answers. The repository answers “no such coupon”; the aggregate answers “this coupon cannot be redeemed”. Keeping them apart is why FindByIdOrThrow lives on the port, not inside the entity.
  • The guard is a check, not a lock. version is stored on the aggregate, but Save does not compare it: two simultaneous redeems can both pass the quota guard and both write. If you need a hard guarantee, the write itself has to be conditional — a compare-and-set on version, or an atomic $inc that includes the quota in its filter.
  • Redeem is deliberately not idempotent. Calling it twice spends two redemptions. deleteCoupon does return early when already deleted — that is a delete, not a spend.
  • Mutating an aggregate raises on the aggregate. The service never constructs CouponRedeemedEvent; it only drains what the aggregate collected.

4.1

Reads — contract queries on the query bus

Three files, three owners. The provider writes the class, the handler, and the registration. The consumer only imports and executes.

Why this is safe: the query bus is a Map<QueryConstructor, Handler>. The consumer's class object is the key. Same import path ⇒ same object ⇒ handler found. This is also the failure mode to watch — see the next callout.

Symptom: Error: No handler registered for VerifyCategoryAndGetQuery at runtime, even though the string type matches and the handler is imported. Cause: two class objects. Fix: delete the local class and re-export from @ecomerece/contracts. This exact bug existed in inventory and was fixed on 2026-11-09.

Registering twice throws. InMemoryQueryBus.register raises Handler already registered for <Name>. That is intentional: it turns a double-wiring mistake into a startup failure instead of a silent shadowing.

The counter-example. Everything above is a read that another module owns. The public product list is a read this module owns, and it never touches the bus — which is the distinction most readers miss.

  • The rule is ownership, not read vs write. getPaginatedProducts is a read owned by product, so the controller calls its own app service and the query bus is never involved. getProductContext is a read owned by two other modules, so it is a contract query on the bus. Same layer, different wiring.
  • The filter is the authorization. There is no authMiddleware on this route at all; what keeps a draft or a blocked product out of the response is the base filter (deleted, block, appearance), applied before any user parameter.
  • Keyset, not offset. The cursor is base64url({ v, id }) and the sort is a keyset on _id or stats.*. No skip() means page 900 costs the same as page 1 and inserting a product cannot shift a row onto the next page.
  • limit + 1 is how hasMore is known. One extra document, sliced off before mapping: no second countDocuments() per request.
  • direction=prev flips the query, not the array. The repository reverses the sort, then the caller reverses the rows back, so the page reads left to right either way.
  • .lean() then a mapper. Plain objects go into persistenceToAggregate and out through the response read model — a Mongoose document never reaches the socket.
4.2

Actions — typed ports, injected adapters

When a module must change something another module owns, use a port. There is no command bus: a missing handler is a TypeScript error at the factory, not a runtime throw.

Why ports instead of events here? Reserving stock is a decision the caller must wait for and must be able to fail. Events are fire-and-forget and cannot roll back the caller. If the answer matters, it is a query or a port — never an event.

Port hygiene. The interface contains domain types only (Id, Quantity, read models) — never a Mongoose document, never a class from the provider's application layer. The adapter body is allowed to know everything; the contract is not.

4.3

Reactions — domain events

Events decouple the publisher from an unknown number of consumers. The publisher owns the event class; consumers only know the string.

Semantics you can rely on (and must not fight):

  • Handlers for one event run concurrently via Promise.allSettled; one rejection is logged and does not block the others.
  • No ordering guarantee between handlers — do not build a pipeline where handler B assumes handler A finished.
  • Unknown event types are ignored; an event with no handler is dropped silently (EVENT_BUS_DEBUG=true logs it).
  • Registration is idempotent (a Set), so double registration does not double-fire.
  • Publishing from a request is awaited — “fire and forget” means the caller does not branch on the result, not that you skip the await.

Real consequence in this repo. The three stats.product-denormalization-requested handlers (product, category, vendor) used to run sequentially. With allSettled they now start together, so category/vendor roll-ups can read product stats mid-refresh. Do not “fix” this by making the event bus sequential again; make the handlers idempotent or chain an explicit second event.

4.4

Middleware ports — configure*()

Middleware sits outside the module graph, so it cannot take constructor deps. The pattern is a module-level configuration hook called once from the composition root.

Why not import UserModel in the middleware? That is exactly the coupling the refactor removed. The middleware may be instantiated in isolation, and the user module owns its model. The adapter is the seam; the composition root chooses the implementation.

4.5

Cross-module transactions — one session, one commit

When two modules must write atomically, the consumer opens the transaction and the providers' repositories join it implicitly through AsyncLocalStorage.

Never publish inside the transaction. A consumer may query a different connection and see pre-commit state, or the transaction may abort after the event already fired. Collect events in the callback, publish after it resolves. This is tested by apps/api/modules/order/application/__tests__/order-create-commit.test.ts.

Replica set required. Mongo transactions need ?replicaSet=rs0 and a real replica set. Without one, the order flow fails at startTransaction — a local single-node mongod is not enough.

4.8

One order, end to end — the write that uses every channel

POST /order/create/my is the hardest use case in the repo: HTTP, six contract queries, two ports, three modules and one commit. The animation is the whole request — nothing is elided.

  • Six queries, zero reads of another module's table. The order module never touches a product or inventory document; it asks the owner through the bus.
  • Two ports, one session. IInventoryReservation and IOrderItemsWriter are just interfaces here — the adapters that make them real were injected in step 12 of the walkthrough.
  • Events leave last. Everything before the commit is undoable; everything after it is a consequence the rest of the system is allowed to see.
4.9

No request at all — the stats refresh tick

Everything above started at a socket. ProductStatsSyncScheduler starts at boot and fires on a timer, which changes two things: there is no dbMiddleware to open Mongo, and there is no request to fail — a bad tick has to clean up after itself.

  • The scheduler publishes; it does not write. That one decision is why the admin “data correction” and the vendor force-refresh button are the same code path as the timer.
  • Connect yourself, or buffer. A handler reached from a request can assume the connection; a handler reached from a timer cannot. Call connectDB() at the top.
  • Guards live in the scheduler, not the handler. If you put “is it due?” inside the handler, every manual trigger inherits it and starts silently doing nothing.
  • The effective interval is the smaller of the two settings. min(intervalHours, maxStalenessHours) decides the next run, so an operator who wants fresher numbers can lower either one.
  • The handler is idempotent because it writes absolutes. It $sets recomputed metrics instead of incrementing counters, so a force-refresh, a crash-and-retry and the ordinary tick all converge on the same document.

IDs: who generates what, and when

Every create*/add* path calls Id.create() with no argument. Existing-resource paths (update, delete, lookup, Ensure*) call Id.create(value) to validate a client string. Mappers use Id.rehydrate(value) because persistence is already trusted. Getting this wrong is a security bug, not a style issue.

Why does the query bus say “No handler registered” when the handler exists?

Class identity. The provider registered a class from @ecomerece/contracts/modules/x; the consumer passed an instance of a locally declared class with the same name. type is metadata, not the key. Fix by re-exporting, never by copying. The inventory module had exactly this bug.

Why did my second publish of the same event not double-fire?

Handlers are stored in a Set per event type, so registering the same handler instance twice is a no-op. Two different instances both fire.

The bus files still export a singleton at the bottom — can I import it?

No. in-memory-query-bus.ts and in-memory-event-bus.ts end with export { queryBus } / export { eventBus } left over from the pre-refactor wiring. Nothing imports them; the composition root creates its own instances. Importing the singleton would create a second, empty bus and reproduce the “handler not registered” bug.

Ordering: can one event handler rely on another?

No. Promise.allSettled starts every handler for a type at once, and handlers for different events are simply awaited in array order. Encode sequence as separate events (order.created then order.items-written) or make each handler independent and idempotent.

Transactions: what does the repository need from me?

Nothing, if you use MongoRepository inside unitOfWork.transaction — it reads the ambient session. What you must do: use startTransaction/commit/abort only through UnitOfWork, never a raw session, and never publish inside the callback.

Optimistic locking: why did my save return 0 modified documents?

The aggregate you loaded has a stale version, or the update payload is identical to what is stored (Mongo reports modifiedCount: 0 for a no-op). Check that the command actually changed state; if it did, reload and retry — do not remove the version predicate.

Leftovers you should not copy
  • order.returnded — typo in the event type; renaming is a breaking change for handlers.
  • /order-items router is mounted but empty; the module is internal and wired through IOrderItemsWriter.
  • CategoryInternalServcie, product-varaint.routes.ts — historical typos kept for import stability. New files spell things correctly.
  • AGENTS.md's four-method mapper naming does not match the mappers in the tree.

auth, admin is the standard admin chain; reversing it lets an unauthenticated caller reach the role check and get 403 instead of 401. statsViewGuard goes on write paths, statsAccessGuard on reads. middleware/seller.ts reads c.get('profile'), which nothing sets — do not mount it as-is.
